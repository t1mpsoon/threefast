# ThreeFast: обед без ожидания

Веб-сервис предзаказа еды к точному времени для кафе, фудкортов и столовых.
Гость собирает заказ **за 3 шага без регистрации**, выбирает точное время получения
и забирает готовый заказ по короткому коду — без очереди на кассу и на кухню.

Реализация кейса «ThreeFast: Обед без ожидания» (направление BUSINESS, хакатон FIZTEX).

---

## Быстрый старт

- Windows: двойной клик по `start.bat`
- Linux/macOS: `./start.sh`
- Docker: `docker compose up --build`

Скрипт сам создаст окружение, БД, демо-заказы и откроет сайт: гость `/`, кухня `/staff`, суперадмин `/super`, API `/docs`. Логины и пароли выводятся в консоль при первом запуске (`.env`). Сайт можно установить на телефон как приложение (PWA).

## 1. Проблема и решение

**Проблема.** В часы пик гость тратит до 20 минут на оформление и ожидание заказа:
очередь на кассу, затем ожидание на кухне. Заведение в это же время физически
не может обслужить больше людей — пропускная способность упирается в очередь,
а не в кухню.

**Решение.** Заказ оформляется заранее из браузера:

1. Гость открывает сайт заведения по QR-коду со стола (приложение устанавливать не нужно).
2. Выбирает блюда и **точное время получения** из свободных слотов.
3. Указывает имя и телефон — и всё.

Кухня видит очередь заказов, распределённую по слотам, и готовит их **ровно к нужному
времени**. Гость приходит к назначенному моменту, называет код — заказ уже ждёт.
Система не даёт забронировать больше заказов на слот, чем кухня успевает приготовить,
поэтому нагрузка распределяется равномерно, а пики сглаживаются.

**Кто пользуется:**

| Роль | Что делает | Нужен ли вход |
|---|---|---|
| Гость | Заказывает еду к точному времени | Нет — только имя и телефон |
| Кухня заведения (staff) | Ведёт очередь **своего** заведения: готовит, отмечает готовность и выдачу, правит меню | Да, логин/пароль |
| Администратор (admin) | То же плюс аналитика и настройки вместимости кухни | Да, логин/пароль |

Супер-администратор сервиса (`superadmin`) заводит новые заведения на странице
`/super` и выдаёт им логин с паролем.

У каждого заведения свой аккаунт кухни (`kitchen-central`, `kitchen-bowl`,
`kitchen-coffee`): смена видит только свои заказы, чужое меню править не может.

## 2. Как выполняются критерии успеха кейса

### Ограничение «оформление не более чем за 3 шага»

Флоу физически состоит из трёх экранов, и ни на одном нет регистрации:

| Шаг | Экран | Что происходит | Код |
|---|---|---|---|
| 1 | `/e/{id}/menu` | Выбор блюд, корзина в localStorage | `menu.html`, `menu.js` |
| 2 | шторка «Когда заберёте» | Выбор времени получения из доступных слотов | `partials/sheet_time.html`, `sheet_time.js` |
| 3 | шторка «Оформление заказа» | Имя, телефон, примечание, оплата | `partials/sheet_checkout.html`, `sheet_checkout.js` |

Шаги 2 и 3 — нижние шторки поверх меню, а не отдельные страницы: гость не теряет
корзину и не ждёт загрузки. Прежние адреса `/e/{id}/slots` и `/e/{id}/confirm`
отдают редирект на меню, чтобы внешние ссылки не ломались.

Ни логина, ни пароля, ни SMS: гость вводит только имя и телефон. Телефон нужен,
чтобы связаться с гостем, а не для идентификации личности.

### Критерий «ожидание выдачи 20 минут → 2 минуты»

Ожидание сокращается не лозунгом, а механикой слотов:

- время получения выбирает сам гость — слоты строятся с шагом 5 минут (настраивается);
- слот недоступен, если до него меньше времени, чем нужно на приготовление самого
  долгого блюда в корзине (правило Б-1) — то есть к моменту прихода гостя заказ
  гарантированно готов;
- система измеряет фактический результат: `average_wait_minutes` = время от слота
  до фактической выдачи (`picked_up_at`), а не время с момента заказа.

Метрика видна на дашборде `/admin/analytics`, цель кейса (≤ 2 минут) подсвечивается
зелёным при выполнении.

### Критерий «рост пропускной способности ≥ 25%»

- Вместимость слота (`slot_capacity`) и длительность слота
  (`slot_duration_minutes`) настраиваются администратором — это прямой рычаг
  пропускной способности;
- теоретическая ёмкость считается как `(60 / длительность слота) × вместимость`
  и показывается в заказах в час;
- фактический рост = `(заказов за период − эталон × дней) / (эталон × дней) × 100%`,
  где эталон «до внедрения» администратор вводит вручную: система не может знать
  статистику заведения до своего появления.

## 3. Быстрый старт

Требуется Python 3.11+ (проверено на 3.14).

### Windows (PowerShell / cmd)

```powershell
python -m venv venv
venv\Scripts\activate
pip install -r requirements.txt
copy .env.example .env
python -m app.init_db
uvicorn app.main:app --reload
```

### Linux / macOS

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
python -m app.init_db
uvicorn app.main:app --reload
```

После запуска:

| Что | Адрес |
|---|---|
| Список заведений | http://127.0.0.1:8000 |
| Меню заведения | http://127.0.0.1:8000/e/1/menu |
| Мой заказ (по номеру) | http://127.0.0.1:8000/order |
| Очередь для персонала | http://127.0.0.1:8000/staff |
| Панель администратора | http://127.0.0.1:8000/admin |
| Сводка | http://127.0.0.1:8000/admin/analytics |
| Документация API (Swagger) | http://127.0.0.1:8000/docs |
| Проверка работоспособности | http://127.0.0.1:8000/health |

Фотографии блюд и заведений кладутся в проект отдельной командой (нужны один раз,
для демонстрации они уже скачаны):

```powershell
venv\Scripts\python.exe -m tools.fetch_photos
```

### Тестовые учётные данные

Пароли **не хранятся в коде**: при первом `python -m app.init_db` они генерируются
случайно и печатаются в консоль один раз (либо берутся из `SEED_ADMIN_PASSWORD`
и `SEED_STAFF_PASSWORD` в `.env`, если заданы).

```
логин: superadmin       роль: администратор сервиса  (заведения, доступы)
логин: admin            роль: администратор заведения (очередь, меню, настройки, аналитика)
логин: staff            роль: кухня                  (очередь заказов)
логин: kitchen-central  роль: кухня                  (только «Кафе Central»)
логин: kitchen-bowl     роль: кухня                  (только «Green Bowl»)
логин: kitchen-coffee   роль: кухня                  (только «Кофе и выпечка»)
логин: place-2          роль: администратор          (только «Green Bowl»)
логин: place-3          роль: администратор          (только «Кофе и выпечка»)
```

Схема логинов одна: `place-<номер>` — администратор точки, `kitchen-<номер>` —
её смена. У трёх точек из начальных данных кухонные логины читаемые
(`kitchen-bowl` и т. д.), их задаёт `app/init_db.py`.

Администратор сервиса не относится ни к одному заведению: в разделе
«Заведения» у каждой точки видны её собственные доступы — администратор точки
и смена кухни, подписанные названием кафе.

В интерфейсе есть кнопка возврата к началу страницы: появляется после
прокрутки, работает на всех экранах — и в меню, и в панели кухни.

Пароль `superadmin` берётся из `SEED_ADMIN_PASSWORD` (если пусто — генерируется и
печатается один раз, как у остальных). Создаётся, пока `SEED_SUPERADMIN=true`;
логин настраивается через `SEED_SUPERADMIN_USERNAME`. Войти им можно на
http://127.0.0.1:8000/login — он попадёт сразу в раздел заведений `/super`.

Пароль у всех аккаунтов кухни один — значение `SEED_STAFF_PASSWORD`. Вход:
http://127.0.0.1:8000/login, после входа смена попадает в свою панель
(http://127.0.0.1:8000/staff).

Если пароль забыт — пересоздайте базу: `python -m app.init_db --reset`
(все данные будут удалены, пароли выведутся заново).

> В базе этого стенда дополнительно созданы `demo_admin` и `demo_staff`
> с паролем `demo-pass-12345` — чтобы панели можно было открыть, не восстанавливая
> пароли от `admin` и `staff`. На чистом окружении их не будет.

### Обязательная правка `.env`

```ini
SECRET_KEY=<случайная строка>
```

Сгенерировать: `python -c "import secrets; print(secrets.token_urlsafe(48))"`.
В `development` при пустом ключе он генерируется на время процесса (с предупреждением);
в `production` (`APP_ENV=production`) запуск с небезопасным ключом падает с ошибкой.

## 4. Как проверить за 3 минуты (сценарий демонстрации)

1. Открыть http://127.0.0.1:8000 — список заведений с фото, рейтингом, временем
   до готовности и загрузкой кухни. Вход не требуется.
2. Выбрать заведение (лучше то, где на бейдже «Свободно сейчас») — откроется меню.
   Добавить 2–3 блюда: кнопка «+» превращается в степпер, снизу выезжает панель
   с суммой.
3. Нажать на панель — снизу выедет шторка выбора времени. Выбрать минуту
   и нажать «Подтвердить время» (если сегодняшние минуты прошли, нажать «Позже»).
4. В открывшейся шторке оформления ввести имя и телефон (например,
   `+7 701 123 45 67`), выбрать оплату и нажать **«Оформить заказ · сумма»**.
5. Появится экран «Заказ EX-… принят» с галочкой, временем получения и прогрессом
   из четырёх сегментов.
6. Открыть http://127.0.0.1:8000/login и войти как `demo_staff` или `staff` — заказ
   виден в очереди с обратным отсчётом. Провести по статусам:
   «Начать готовить» → «Отметить готовым» → «Отдал гостю» — прогресс на экране
   гостя обновится.
7. Войти как `demo_admin` или `admin` → «Сводка»: среднее время ожидания, число
   заказов и рост пропускной способности относительно эталона «до внедрения».

Чтобы очередь кухни было на что смотреть, можно наполнить её тестовыми заказами:

```powershell
venv\Scripts\python.exe -m tools.seed_demo_orders
```

Автоматический прогон всего этого по HTTP без браузера:

```powershell
venv\Scripts\python.exe smoke_test.py
```

## 5. Интерфейс

Современный интерфейс доставочного сервиса: понятный с первого взгляда, дружелюбный,
с акцентом на фото еды и скорость сценария. Никаких сложных метафор — гость видит
знакомый паттерн: список заведений → меню → шторка выбора времени → шторка оформления →
экран отслеживания. Полное описание — в [`docs/design.md`](docs/design.md).

**Палитра:** фон `#FFFFFF`, второстепенные блоки `#F4F5F7`, текст `#1B1D21`,
вторичный текст `#6B7280`, акцент **Flame `#FF4F32`** (выбран под смысл продукта —
скорость и «горячий готовый заказ»), статусы `#12B76A` «готово» и `#F79009`
«небольшая очередь». Акцент стоит только на ключевых действиях: CTA, активная
капсула, таймер, бейдж — не разбросан по интерфейсу.

**Две темы.** Светлая по умолчанию, тёмная — по выбору гостя; выбор запоминается
в браузере и ставится до первой отрисовки, чтобы светлая не мигнула. Переключатель
есть в шапке и в нижней навигации на телефоне.

**Акцент системный, не точечный.** На главном экране Flame встречается десять раз,
в меню — больше тридцати: иконка геолокации, активная капсула категории, градиент
промо поверх фото, бейдж времени, звезда рейтинга, кнопка «+» на карточке блюда,
панель корзины, выбранный слот, текущий сегмент прогресса.

**Форма:** три роли радиуса — 20px у крупных карточек, 12px у иконок внутри них, капсула 999px у кнопок и чипов.
Тени едва заметные: под фото-карточками, капсулами поверх фотографий и
всплывающими слоями; под текстовыми блоками теней нет.

**Типографика:** Plus Jakarta Sans, два начертания — жирное для заголовков, цен
и CTA, обычное для описаний. Цены всегда полужирные и чуть крупнее описания.

**Экраны:**

1. **Главная** — адрес пикапа с живыми часами, поиск (ищет по заведению, улице,
   кухне и блюдам), промо-баннер на фото-подложке с градиентом акцентом, отсчёт до
   ближайшего окна выдачи, список заведений одинаковыми карточками (быстрое помечено
   бейджем «Быстрее всего»), витрина блюд из нескольких заведений, сводка из трёх
   плиток и блок «Как это работает». Внизу навигация «Заведения / Мой заказ /
   Для смены». Данные главной приходят одним запросом.
2. **Меню заведения** — баннер с фото, который сворачивается в компактную
   sticky-шапку при скролле; липкая лента категорий, синхронизированная со скроллом;
   сетка карточек блюд: фото 4:3 сверху, название, описание, крупная жирная цена,
   белая капсула «+» на углу фото, превращающаяся в степпер прямо на месте.
3. **Шторка выбора времени** — выезжает снизу поверх меню, слоты капсулами,
   сгруппированные по получасу («Ближайшее», «13:00–13:30»…). Занятые минуты —
   приглушённый текст без заливки, выбранная — заливка Flame.
4. **Шторка оформления** — имя, телефон (без пароля, логина и SMS), капсульный
   переключатель «Наличными / Картой», сводка заказа и кнопка
   «Оформить заказ · сумма».
5. **Экран заказа** — кастомная SVG-галочка с отрисовкой обводки, крупное время
   получения, прогресс из четырёх сегментов с плавным заполнением, кнопка
   «Поделиться заказом».

**Панели персонала и админа** — те же токены и типографика, но тише: список заказов
плотными строками, обычные таблицы меню, метрики смены. Вся выразительность
сосредоточена в клиентском флоу.

**Микро-интеракции:** скелетоны вместо спиннера, пружина степпера
(scale 1 → 1.08 → 1, 200 мс), всплывающая и тающая плашка «+1», мягкий подъём
панели корзины, шторка со свайпом вниз, увеличение фото внутри карточки при
наведении (сама карточка неподвижна).

**Сканер заказов** (`/scan`, кухня и админ) читает QR гостя двумя декодерами:
сначала встроенный `BarcodeDetector`, если браузер его умеет, иначе — `jsQR`
из `app/static/js/vendor`. Если камеры нет, она запрещена или браузер не
запускает поток без касания, остаются загрузка фото QR и ручной ввод номера:
эти пути работают в любом браузере. Ни одного внешнего запроса страница
не делает — недоступный CDN однажды уже оставил сканер без декодера.

**Фото** лежат локально в `app/static/img/menu` и `app/static/img/places`
(скачиваются командой `python -m tools.fetch_photos`, источник — Unsplash),
поэтому демонстрация работает без интернета. Для реального заведения их нужно
заменить на фотографии своих блюд — поле `photo` есть в админке.

Свежие снимки всех экранов — в `shots/`.


**Поток данных при оформлении заказа (шаг 3):**

```
Браузер (fetch, idempotency_key)
  → POST /api/orders              routers/orders.py
      → валидация тела            schemas/order.py (Pydantic)
      → OrderService.create_order services/order_service.py
            → проверка дубля по idempotency_key
            → проверка блюд и расчёт суммы (правило В-1)
            → SlotService.validate_slot_choice (правило Б-1)
            → SlotRepository.try_reserve — атомарный UPDATE (правило А-2)
            → запись orders + order_items со снапшотом цен
            → commit
  ← 201 {order_code, slot_datetime, total_amount}
```

Слои не смешиваются: `routers/` не обращаются к БД напрямую, `repositories/`
не содержат бизнес-правил, вся логика — в `services/`.

### Стек и почему именно он

| Технология | Зачем | Почему выбрана |
|---|---|---|
| FastAPI + Uvicorn | HTTP API и серверный рендеринг | Автодокументация `/docs`, валидация через Pydantic, минимум шаблонного кода |
| Pydantic v2 | Валидация входных данных | Сообщения об ошибках по каждому полю «из коробки» |
| SQLAlchemy 2.0 | ORM | Параметризованные запросы (защита от SQL-инъекций), переносимость на PostgreSQL |
| SQLite | Хранение данных MVP | Не требует отдельного сервера, достаточно для прототипа и демонстрации |
| Jinja2 + ванильный JS | Интерфейс | Быстрее в разработке, нет сборки и зависимостей фронтенда |
| APScheduler | Авто-истечение невостребованных заказов | Лёгкий планировщик; Celery/RabbitMQ для MVP избыточны |
| bcrypt | Хэширование паролей персонала | Стандарт для паролей, используется напрямую |
| python-jose (JWT) | Сессии персонала | Stateless-авторизация для внутренних панелей |
| Alembic | Версионирование схемы БД | Позволяет менять схему без пересоздания базы |

## 7. Бизнес-правила

| Правило | Содержание | Где в коде |
|---|---|---|
| А-1 | Слот недоступен, если до него меньше времени приготовления; заполненный слот помечается занятым | `services/slot_service.py` |
| А-2 | Проверка и увеличение занятости слота — одним атомарным `UPDATE ... WHERE booked_count < capacity` | `repositories/slot_repository.py::try_reserve` |
| Б-1 | Время приготовления заказа = максимум по блюдам корзины | `services/order_service.py` |
| Б-2 | Разрешены только переходы `confirmed → in_progress → ready → picked_up`, отмена из активных статусов | `models/order.py::ALLOWED_TRANSITIONS` |
| Б-3 | Заказ, готовый и не востребованный 20 минут, переходит в `expired` | `services/order_service.py::expire_stale_orders`, `services/scheduler.py` |
| В-1 | Сумма = Σ(цена × количество); цены фиксируются в `order_items` | `services/order_service.py::calculate_total` |
| Г-1 | Слоты сортируются по возрастанию времени | `services/slot_service.py::build_slots` |

### Статусы заказа

```
confirmed ──→ in_progress ──→ ready ──→ picked_up
    │              │            │
    └──────────────┴────────────┴──→ cancelled   (гость или персонал)
                   │            │
                   └────────────┴──→ expired      (автоматически, 20 мин после ready)
```

**Пример создания заказа:**

```bash
curl -X POST http://127.0.0.1:8000/api/orders \
  -H "Content-Type: application/json" \
  -d '{
    "establishment_id": 1,
    "slot_datetime": "2026-09-20T13:05:00",
    "guest_name": "Аружан",
    "guest_phone": "+77011234567",
    "items": [{"menu_item_id": 1, "quantity": 2}],
    "payment_method": "cash_on_pickup",
    "idempotency_key": "уникальный-ключ-на-каждую-попытку"
  }'
```

**Коды ответов:**

| Код | Когда |
|---|---|
| 200 | Успех; для повторного `POST /api/orders` с тем же `idempotency_key` — тот же заказ |
| 201 | Заказ создан |
| 400 | Некорректные данные, прошедшие схему (прошедшая дата, недопустимый переход статуса) |
| 401 | Нет или истёк токен |
| 403 | Недостаточно прав (например, `staff` запрашивает аналитику) |
| 404 | Заведение, блюдо или заказ не найдены |
| 409 | Слот занят (`slot_unavailable`) или конфликт версий (`version_conflict`) |
| 422 | Ошибка валидации; в теле `fields` — сообщение по каждому полю |
| 429 | Слишком много заказов с одного IP за минуту |

## 9. Безопасность и целостность данных

- **Без регистрации гостя** — по требованию кейса; идентификация заказа по случайному
  коду `EX-XXXX`, а не по последовательному ID, поэтому перебрать чужие заказы нельзя.
- **Пароли** хранятся только как bcrypt-хэши; **JWT** подписывается `SECRET_KEY` из `.env`.
- **Секреты** не попадают в репозиторий: `.env` в `.gitignore`, в коде только
  заведомо небезопасные значения для `development`.
- **Логи** маскируют телефоны (`7701***67`), токены и хэши — даже при неаккуратном
  вызове логгера (см. `logging_utils.scrub`).
- **SQL-инъекции** исключены: только ORM и параметризованные запросы.
- **Дубли заказов** отсекаются уникальным `idempotency_key` (защита от двойного клика
  и обрыва связи): повторный запрос возвращает уже созданный заказ.
- **Переполнение слота** невозможно: резервирование — атомарный `UPDATE` с условием
  `booked_count < capacity`, проверено конкурентным тестом на 5 одновременных запросов.
- **Конкурентная смена статуса** двумя сотрудниками разрешается optimistic locking
  по полю `version`: второй запрос получает 409 и перечитывает данные.
- **Права доступа**: сотрудник работает только с заказами своего заведения;
  меню, настройки и аналитика доступны только администратору.
- **Rate limiting**: не более `RATE_LIMIT_ORDERS_PER_MINUTE` заказов с одного IP в минуту.
- **Ошибки**: пользователь никогда не видит traceback — все исключения перехватываются,
  логируются и превращаются в понятное сообщение (JSON для API, страница для браузера).

## 12. Границы MVP (что сознательно не сделано)

- **Нет регистрации гостей** — прямо запрещена условием кейса.
- **Нет реального платёжного шлюза** — способ оплаты в задании не указан; в MVP
  работает «оплата при получении», интерфейс готов к подключению провайдера.
- **Нет нативного мобильного приложения** — задание допускает веб-сайт, а веб быстрее
  в разработке и не требует установки.
- **Нет SMS/push-уведомлений** — статус отслеживается по ссылке `/order?code=...`
  с автообновлением; внешние сервисы рассылок не подключены.
- **Нет PostgreSQL/Redis/очередей** — для одного заведения и демонстрации достаточно
  SQLite и APScheduler; переход на PostgreSQL не требует изменения бизнес-логики.
- **Две роли** (staff и admin) вместо сложной ролевой модели.
- **Нет i18n и ML-прогнозов** — только фактическая аналитика, как требует задание.

## 13. Частые вопросы при запуске

**`Заведение не найдено. Запустите python -m app.init_db`** — база пуста, выполните
`python -m app.init_db`.

**«На этот день свободных слотов нет»** — либо заведение уже закрылось (по умолчанию
09:00–18:00), либо все слоты заняты. Выберите другую дату кнопкой «Завтра».

**«Выбранное время только что заняли» (409)** — слот заполнился, пока вы заполняли
форму: система вернёт вас на шаг 2 с актуальным списком слотов, корзина сохранится.

**Порт 8000 занят** — `uvicorn app.main:app --port 8010`.

**Забыли пароль сотрудника** — `python -m app.init_db --reset` (удалит данные
и выведет новые пароли).

## Развёртывание в облаке (Render)

В репозитории лежит `render.yaml` — описание сервиса и базы. Развёртывание
занимает пару минут и не требует правок кода.

1. Зарегистрируйтесь на [render.com](https://render.com) через GitHub.
2. **New → Blueprint**, выберите репозиторий `threefast`.
3. Render прочитает `render.yaml`, создаст веб-сервис и базу Postgres,
   свяжет их и сгенерирует секреты. Нажмите **Apply**.

Что Render делает сам:

| Переменная | Значение |
|---|---|
| `DATABASE_URL` | строка подключения к созданной базе |
| `SECRET_KEY` | генерируется, в репозитории его нет |
| `SEED_ADMIN_PASSWORD`, `SEED_STAFF_PASSWORD` | генерирует Render при создании сервиса |
| `PORT` | передаётся в команду запуска |
| `TZ` | `Asia/Almaty` — часовой пояс слотов заведений |

**Пароли начальных аккаунтов** лежат в переменных окружения сервиса: Render →
сервис `threefast` → вкладка **Environment** → `SEED_ADMIN_PASSWORD` и
`SEED_STAFF_PASSWORD` (значения скрыты, рядом есть кнопка «показать»). В логи
они не печатаются: `app/init_db.py` выводит пароль в консоль только тогда,
когда переменная пустая и пароль генерируется на месте.

Локально приложение работает на SQLite и ничего дополнительно не требует.
На хостинге используется Postgres: `DATABASE_URL` от Render приходит в виде
`postgres://…` и приводится к нужному виду в `app/config.py`.

### Ограничения бесплатного тарифа Render

- Сервис засыпает после 15 минут без запросов; первый запрос после паузы
  отвечает около минуты.
- Бесплатная база Postgres живёт 30 дней, потом её нужно продлить или
  пересоздать. Данные при этом не сохраняются.
- Файловая система временная: база на диске не подошла бы, поэтому выбрана
  managed-база.
